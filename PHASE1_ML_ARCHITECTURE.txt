1. REFRAMED CORE PIPELINE (LOCKED)
================================================================================

Your diagram was directionally right. Alpha production path is:

```text
Market Data (validate + store)
        │
        ▼
Feature Store (point-in-time, versioned)
        │
        ▼
ML Models (offline train → serialized infer)
   ├── Alpha model(s)     → signal / expected return / rank score
   └── Loss model         → P(hit stop) / adverse ES
        │
        ▼
Strategy Engine (rules: when signal is actionable)
        │
        ▼
Portfolio Construction (draft weights / lots)     [CODE]
        │
        ▼
Loss Prediction Gate (skip / cut / flatten / hold) [ML SCORE + policy]
        │
        ▼
Risk Kernel (hard veto / halt / force flatten)     [CODE — absolute]
        │
        ▼
Execution Engine (paper | live flag)
        │
        ▼
Broker API (ONE primary)
        │
        ▼
TCA + Attribution + Monitoring → Trial Registry feedback
```

WHY THIS ORDER (decision)
  Portfolio proposes size → Loss scores path risk on THAT size → Risk enforces
  hard ceilings. Putting Risk before Portfolio hides soft path risk and mixes
  “how big?” with “are we allowed?”. Alpha keeps them separate on purpose.

WHAT “HIGH ACCURACY” MEANS (LOCKED DEFINITION)
  NOT: 80% Buy/Sell classification accuracy on random split
  YES: Out-of-sample, cost-aware metrics that survive purge/embargo:
        - Net Sharpe / Sortino / Calmar after brokerage+STT+slip+lots
        - Max DD within policy
        - Turnover & capacity sanity
        - Loss-model calibration (reliability of P(hit stop))
        - Paper shortfall vs backtest within agreed band
  A model with “55% direction accuracy” can be excellent mid-freq IF
  sizing/risk/costs work. Accuracy% alone is vanity.

3.5 RISK MANAGEMENT vs PORTFOLIO (SPLIT — IMPORTANT)
-----------------------------------------------------------------------------

Your doc mixed sizing, stops, VaR, sector limits under “Risk”.
Alpha splits for clarity and veto power:

PORTFOLIO CONSTRUCTION (CODE) — draft
  - Convert scores → target weights / lots
  - Gross/net budgets, single-name caps (soft proposals)
  - Simple method P1: score → rank → capped equal-risk or fixed ₹ risk per trade
  - DEFER: Black-Litterman, HRP, full Markowitz (add only if multi-asset book needs)

LOSS PREDICTION (ML) — soft gate
  - Score draft: skip / reduce / flatten / hold
  - Prefer flat when path risk bad

RISK KERNEL (CODE) — hard gate
  - max daily loss, max DD halt, leverage/margin ₹, concentration
  - kill switches (feed loss, broker disconnect)
  - Absolute veto — no override
  - Stop-loss / flatten POLICY lives here as code limits + runbooks
    (per-trade stops may also be strategy rules — still enforced by kernel)

VaR / CVaR
  Phase 1: simple DD + daily loss + ES from loss model is enough
  Formal VaR engine: DEFER until capital scale needs it

  NOTE ON THE LOSS GATE: the locked design used an absolute P(hit stop)
  threshold. That is unworkable -- a genuine 1:4 setup is supposed to hit its
  stop most of the time, so any fixed cutoff either blocks everything or means
  nothing. Thresholds are now relative to each trade's cost-aware break-even
  probability, and the kernel independently vetoes negative expected value.
  See alpha-desk/docs/DECISIONS_LOCKED.md section 3.

  NOTE ON PORTFOLIO LIMITS: gross-notional multiples do not work for F&O (one
  NIFTY lot is ~Rs 18L notional on Rs 10L equity). Limits are expressed as
  margin utilisation, matching the README's "prefer margin-risk Rs limits".
  At Rs 10L the cap is 30%, which funds exactly one index futures lot. HoQR's
  requested 10-20% cannot fund even one lot -- see DECISIONS_LOCKED.md s4.

  time exits, not by the 1:2 barrier. The horizon/stop pairing needs a sweep in
  P1.3 before any promote decision.
